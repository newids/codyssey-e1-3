# Mission 3 — Mini NPU Simulator

AI가 계산하는 방식(MAC, Multiply-Accumulate)을 흉내 내는 작은 계산기.
입력 패턴과 필터를 같은 위치끼리 곱해 모두 더한 점수로 십자가(Cross)/X 패턴을 판별하고,
필터 크기(3×3 ~ 25×25)에 따른 연산 시간 변화를 측정.

## 1. 산출물 위치와 상태

| 산출물 | 위치 | 상태 |
| --- | --- | --- |
| 메인 실행 파일 | [`main.py`](main.py) | 모드 1/2 + 보너스 B1·B2 |
| 제출 문서 | `README.md` (본 문서) | 실행 방법 + 구현 요약 + 결과 리포트 10줄 이상 |
| 데이터 | [`data.json`](data.json) | 제공본 그대로 (수정 금지) |

**기대 결과(정답지)**: 모드 2 실행 시 `총 6 / 통과 3 / 실패 3`.
실패 3건은 버그가 아니라 데이터 설계상의 수학적 동점 — 근거는 §7-2에 정리했음.

## 2. 실행 방법

```bash
python3 main.py
```

- 실행 환경: **Python 3.8 이상** (실측 검증: Python 3.9.6 / 3.13.5, macOS)
- 외부 라이브러리 없이 표준 라이브러리(`json`, `os`, `time`)만 사용
- `data.json`은 `main.py`와 같은 디렉터리에 두면 됨
  (스크립트 위치 기준 절대 경로로 찾으므로 어느 디렉터리에서 실행해도 동작함)

실행하면 모드 선택 메뉴가 나옴.

| 선택 | 모드 | 동작 |
| --- | --- | --- |
| `1` | 사용자 입력 (3×3) | 필터 A·B와 패턴을 한 줄씩(공백 구분) 입력 → 저장 확인 → 점수/판정/시간 → 3×3 성능 분석 |
| `2` | data.json 분석 | 필터 로드 → 케이스별 판정·PASS/FAIL → 성능 분석(2차원/1차원) → 결과 요약 |
| `3` | 패턴 생성기 (보너스) | 크기 N 입력 → N×N Cross/X 패턴 생성 → 자체 검증 → 성능 측정 |
| `Q` | 종료 | |

## 3. 구현 요약

- **MAC 연산**: 벡터화 라이브러리 없이 2중 반복문으로 위치별 곱→누적합을 직접 구현
  (`mac()`). 보너스로 2차원 배열을 1차원(길이 N²)으로 펼쳐 접근하는 버전(`mac_flat()`)을
  구현해 성능을 비교.
- **라벨 정규화**: `expected` 값(`'+'`/`'x'`)과 필터 키(`'cross'`/`'x'`)를 모두 내부 표준
  라벨 `Cross`/`X`로 변환(`normalize_label()`)한 뒤 판정·비교.
- **동점 처리(epsilon)**: 점수 차이가 `1e-9` 미만이면 판정하지 않고 `UNDECIDED`
  (모드 1은 "판정 불가")로 처리. 판정은 단일 함수 `decide()`로 일원화.
- **스키마/크기 검증**: 패턴 키에서 N을 추출해 해당 필터를 선택하고, 필터·패턴이 N×N인지
  검증(`validate_size()`). 오류(크기 불일치, 라벨 오류, 필터 누락 등)는 케이스 단위로
  격리해 해당 케이스만 FAIL 처리하며 프로그램은 중단되지 않음.
- **성능 측정**: `time.perf_counter()`로 I/O를 제외한 MAC 연산 구간만 10회 반복 측정해
  1회 평균 ms를 출력.

### 구현 순서 (실제 진행 순서)

각 단계마다 바로 실행해 확인할 수 있는 단위로 쪼개서 진행.

```text
STEP 1  핵심 연산 계층 (I/O 없음 → 가장 먼저, 가장 쉽게 검증됨)
        mac()              이중 for 루프 곱-누적            → F5
        normalize_label()  '+'/'x'/'cross' → Cross/X       → F4
        decide()           epsilon 1e-9 동점 판정           → F6
        validate_size()    N×N 크기 검증                    → F1
        검증: 미션 예시(X 패턴 입력 → A 1점, B 5점)를 손으로 대조

STEP 2  보너스 생성기 (성능 분석의 재료가 되므로 먼저)
        create_cross(n) / create_x(n)                      → 보너스 B2
        검증: N=5 생성 결과가 가운데 행/열·두 대각선과 일치함을 확인했음

STEP 3  성능 분석
        measure_mac_ms()      perf_counter, 10회 평균, I/O 제외 → F7
        measure_mac_flat_ms() 1차원 버전 (flatten은 측정 제외)  → 보너스 B1
        print_performance()   [3, 5, 13, 25] × (2D, 1D) 표 출력

STEP 4  모드 1 (사용자 입력)
        input_3x3_matrix()  행 수·열 수·파싱 검증, 오류 시 해당 행 재입력 → F2
        print_matrix()      저장 확인 출력 (저장/읽기 증명)
        user_input()        A·B 입력 → 저장 확인 → 패턴 → MAC → 판정 → 3×3 성능

STEP 5  모드 2 (data.json)
        load_filters()      필터 키 정규화 + 크기 검증 + 로드 로그(✓/✗)
        parse_pattern_key() 키에서 (N, 번호) 추출
        evaluate_case()     검증 → 케이스 단위 FAIL (raise로 탈출하지 않음) → F3
        analyze_json()      분석 → 성능 → 요약(총/통과/실패 + 실패 목록)   → F8

STEP 6  README 결과 리포트
        성능 수치는 전부 본인 환경 실행값으로 채웠음 (§7)
```

## 4. 요구사항 ↔ 구현 매핑표 (평가 항목 체크용)

| # | 요구사항 | 구현 위치 (`main.py`) | 확인 방법 |
| --- | --- | --- | --- |
| F1 | N×N 저장 + 위치별 읽기/쓰기, 3~25 크기 | 리스트 행렬 + `validate_size`, `MIN_SIZE`/`MAX_SIZE` | 모드 1 저장 확인 출력, 모드 3 범위 검사 |
| F2 | 3×3 입력 + 행/열·파싱 검증 + 재입력 유도 | `input_3x3_matrix`, `user_input` | 시나리오 3, 4 |
| F3 | JSON 로드, N 추출, 크기 검증, 케이스 단위 FAIL | `load_data`, `parse_pattern_key`, `evaluate_case` | 시나리오 6 |
| F4 | 라벨 정규화 ('+'/'x'/'cross' → Cross/X) | `normalize_label`, `LABEL_MAP` | 모드 2 출력이 항상 Cross/X 표기 |
| F5 | MAC 반복문 직접 구현, 외부 라이브러리 금지 | `mac` (이중 for), import는 json/os/time뿐 | `grep import main.py` |
| F6 | epsilon 1e-9 동점 → UNDECIDED, PASS/FAIL 규칙 | `EPSILON`, `decide` | 시나리오 5의 UNDECIDED 3건 |
| F7 | 크기별 10회 평균(ms), I/O 제외, 표에 N² 포함 | `measure_mac_ms`, `print_performance` | 성능 표 3열 확인 |
| F8 | 총/통과/실패 + 실패 목록(식별자+사유) | `print_summary` | 시나리오 5 |
| B1 | 1D 평탄화 + 전/후 비교 (동일 입력·동일 반복) | `flatten`, `mac_flat`, `measure_mac_flat_ms` | 성능 섹션 보너스 표 |
| B2 | 패턴 생성기 + 성능 분석 재활용 | `create_cross`, `create_x`, 모드 3, `print_performance`가 3×3 재활용 | 시나리오 7 |
| 제출 | README: 실행 방법 + 구현 요약 + 결과 리포트 10줄↑ | 본 문서 §2, §3, §7 | §7이 번호 목록 + 표 포함 |

**설계상 주의점 3가지** :

1. **성능 표의 3×3**: `data.json`에는 `size_3` 필터가 없음. → `print_performance`가
   `create_cross(3)`으로 자체 생성 (보너스 B2를 요구사항 F7에 재활용).
   data.json에서 3×3을 찾으려 하면 안 됨.
2. **총 테스트 개수는 6**: 미션 예시 출력의 "8개"는 참고용 예시일 뿐, 실제 파일 패턴은
   6개. 개수를 하드코딩하지 않고 실제 케이스 수를 세도록 구현(`len(results)`).
3. **FAIL 3건은 정답 동작**: "실패 0개"로 만들려고 epsilon을 빼면 최하위 비트 오차로
   판정하는 셈이 되어 오히려 요구사항 위반. 기본은 원시 MAC + epsilon(3 FAIL)이며,
   원인 분석은 §7-2에 문서로만 제시.

## 5. 실행 결과 (캡처)

### 모드 1 — 사용자 입력 (3×3)

십자가 필터(A), X 필터(B), X 패턴을 예시대로 입력한 실제 출력.

```text
선택: 1
# ---------------------------------------
# [1] 필터 입력
# ---------------------------------------
필터 A (3줄 입력, 공백 구분)
1 / 3 > 0 1 0
2 / 3 > 1 1 1
3 / 3 > 0 1 0
필터 A 저장 확인:
  0 1 0
  1 1 1
  0 1 0
필터 B (3줄 입력, 공백 구분)
1 / 3 > 1 0 1
2 / 3 > 0 1 0
3 / 3 > 1 0 1
필터 B 저장 확인:
  1 0 1
  0 1 0
  1 0 1
# ---------------------------------------
# [2] 패턴 입력
# ---------------------------------------
패턴 (3줄 입력, 공백 구분)
1 / 3 > 1 0 1
2 / 3 > 0 1 0
3 / 3 > 1 0 1
패턴 저장 확인:
  1 0 1
  0 1 0
  1 0 1
# ---------------------------------------
# [3] MAC 결과
# ---------------------------------------
A 점수: 1.0
B 점수: 5.0
연산 시간(평균/10회): 0.001 ms
판정: B
# ---------------------------------------
# [4] 성능 분석 (3×3, 평균/10회)
# ---------------------------------------
3×3 | 2차원: 0.001 ms | 1차원: 0.001 ms | 연산 횟수: 9
```

두 필터에 같은 값을 넣어 동점을 만들면 epsilon 정책이 동작함.

```text
# [3] MAC 결과 (판정 불가)
A 점수: 5.0
B 점수: 5.0
판정: 판정 불가 (|A-B| < 1e-9)
```

잘못된 입력을 넣으면 해당 행만 안내 문구와 함께 재입력을 요구함.

```text
1 / 3 > 1 2
입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.
1 / 3 > x y z
입력 형식 오류: 숫자만 공백으로 구분해 입력하세요.
1 / 3 >
```

## 6. 제출 전 자가 점검 시나리오 (전부 실측 통과했음)

아래 명령을 그대로 복사해 실행하면 됨. `printf`가 대화형 입력을 대신 넣어 줌.

### 시나리오 6 — 비정상 데이터 (비정상 종료 금지)

- ① 크기 불일치 패턴
- ② 필터 없는 `size_7_1` 
- ③ `expected: 'circle'` 
- ④ 형식 위반 키 `foo_bar` 
- ⑤ 라벨이 깨진 필터 세트를 주입해 실행.

실측 결과: 5건 모두 각자 정확한 사유로 케이스 단위 FAIL(또는 필터 로드 ✗) 처리되고,
나머지 정상 케이스는 그대로 판정되며, 성능 분석·요약까지 완주함 (§5 오류 캡처 참고).
→ 통과.

### 시나리오 7 — 보너스 패턴 생성기

```bash
printf '3\n5\nq\n' | python3 main.py
```

기대: 5×5 Cross/X 패턴 출력 + 자체 검증 2건 PASS + 성능 출력. → 통과.

## 7. 결과 리포트

### 7-1. 판정 요약

| 항목 | 값 |
| --- | --- |
| 총 테스트 | 6개 |
| 통과 (PASS) | 3개 (size_5_2, size_13_1, size_25_2) |
| 실패 (FAIL) | 3개 (size_5_1, size_13_2, size_25_1) — 모두 UNDECIDED |

### 7-2. 실패 원인 분석 — 부동소수점 표현 한계

실패한 3건은 데이터/스키마 문제도, MAC 로직 오류도 아니고 **수치 비교 문제**.

1. 세 케이스 모두 Cross 점수와 X 점수가 수학적으로는 같아야 하는 값인데, 실측 차이가
   `size_5_1` ≈ 1.1×10⁻¹⁶, `size_13_2` ≈ 2.7×10⁻¹⁵, `size_25_1` ≈ 1.0×10⁻¹⁵으로
   0이 아님.
2. 원인은 `0.1`, `0.9` 같은 십진 소수가 이진 부동소수점(IEEE 754)으로 정확히 표현되지
   않아, 더하는 순서와 횟수에 따라 마지막 비트 수준의 오차가 누적되기 때문.
   예: `0.9`와 `0.1×9`는 수학적으로 같지만 float 합산 결과는 `0.9` vs
   `0.8999999999999999`로 갈림 (size_5_1의 실제 점수).
3. 이런 값을 `==`나 단순 대소 비교로 판정하면 사실상 난수 판정이 됨. 그래서 본 구현은
   **허용오차(epsilon = 1e-9) 정책**을 적용해 `|Cross − X| < 1e-9`이면 UNDECIDED로
   선언함. 위 3건의 FAIL은 이 정책이 의도대로 동작해 "동점을 억지로 가르지 않았다"는
   증거이며, expected 라벨과 불일치하므로 규칙상 FAIL로 집계했음.
4. 즉 실패를 없애려면 로직 수정이 아니라 데이터 설계(동점이 나지 않는 패턴) 또는 판정
   정책(동점 시 expected 허용 등)의 변경이 필요함.

### 7-3. 시간 복잡도 분석 — O(N²)

N×N 패턴 1회 판정에 필요한 곱셈-누적 연산은 정확히 N²회. 측정 결과(§5 [3] 성능표,
2차원 기준)를 연산 횟수와 비교하면 다음과 같음.

| 구간 | 시간 비 | 연산 횟수 비 (N²) |
| --- | --- | --- |
| 5×5 → 13×13 | 0.012 / 0.003 = **4.0×** | 169 / 25 = **6.8×** |
| 13×13 → 25×25 | 0.039 / 0.012 ≈ **3.3×** | 625 / 169 ≈ **3.7×** |

N이 커질수록 시간 증가 비율이 연산 횟수 비율(N²)에 수렴함. 작은 크기(3×3, 5×5)에서
비율이 어긋나 보이는 것은 파이썬 루프 진입·함수 호출 등 **상수 오버헤드가 연산 자체보다
큰 비중을 차지하기 때문**이며, 이는 O(N²)와 모순되지 않음. 실제 AI 모델이 수백×수백
필터를 수천 개 쓸 때 연산량이 기하급수적으로 늘어나는 이유, 그리고 MAC을 병렬로 처리하는
NPU가 필요한 이유를 이 표에서 그대로 확인할 수 있음.

### 7-4. 보너스 — 1차원 최적화 비교

2차원 배열을 1차원(길이 N²)으로 미리 펼쳐 단일 루프로 접근하면 행 리스트 참조가 사라져
작은 크기에서 소폭 빠름 (3×3: 0.002 → 0.001 ms). 다만 순수 파이썬에서는 인터프리터
오버헤드가 지배적이라 25×25에서는 측정 오차 범위 안에서 비슷함 (0.039 vs 0.043 ms).
메모리 접근 패턴 단순화의 효과는 C/하드웨어(NPU) 수준에서 훨씬 크게 나타나는 최적화.

## 8. 평가 예상 질문과 답

| 예상 질문 | 한 줄 답 | 근거 |
| --- | --- | --- |
| MAC이 뭐고 왜 중요한가 | 곱하고 누적하는 연산. CNN 합성곱의 최소 단위이며 NPU가 병렬화하는 대상 | `mac()`, §7-3 |
| 왜 곱-합이 유사도인가 | 같은 위치가 동시에 켜져 있을 때만 점수가 쌓임 = 내적 = 방향 일치도 | §5 모드 1 캡처 (X 패턴 → B 5점) |
| 라벨 정규화는 왜 하나 | `'+'/'x'/'cross'` 등 표기가 소스마다 달라, 비교 직전에 표준형으로 안 모으면 비교 자체가 무의미 | `normalize_label()`, §3 |
| epsilon은 왜 필요한가 | 0.1은 이진수로 정확히 표현 불가 → 누적 순서만 달라도 최하위 비트가 흔들림 → 노이즈로 판정하지 않겠다는 선언 | §7-2 |
| 왜 FAIL이 3개인가 | 필터 스케일 불일치가 만든 수학적 동점. epsilon을 빼도 3 FAIL이며, epsilon은 이를 UNDECIDED로 정직하게 신고 | §7-1, §7-2 |
| O(N²) 근거는 | MAC 1회 곱셈 횟수가 정의상 N². 실측에서 큰 N일수록 시간 증가율이 연산 횟수 증가율에 수렴 | §7-3 |
| FAIL을 0으로 만들 수 있나 | 데이터 설계 또는 판정 정책 변경으로 가능하나, 기본 요구가 원시 MAC + epsilon이라 분석으로만 제시했음 | §7-2 항목 4 |
| 1D 평탄화가 빨랐나 | 작은 크기에서 소폭 우세였고 N이 클수록 이득이 줄었음. CPython 병목은 메모리가 아니라 인터프리터 오버헤드이기 때문 | §7-4 |
